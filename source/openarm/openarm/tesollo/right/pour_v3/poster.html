Stage-Wise Rewarded RL for Humanoid Bimanual Pouring

This poster is aligned with openarm/tesollo/right/pour_v3. The current implementation learns a right-arm source-cup policy while the left arm stabilizes the target cup. The main message is that pouring should be learned as a staged causal chain: workspace acquisition -> pour-point alignment -> tilt regulation -> bead transfer.

Robot Setup Fixed left target cup + learned right source cup
Action 11D policy output: 6D palm target + 5D finger control
Observations 60D actor / 140D critic asymmetric learning
Training View Teleop demo reference + Isaac rollouts + staged RL reward

Core Thesis

Direct end-to-end RL often fails because the true pouring reward appears only after a long sequence of prerequisite motions. In this task, the policy must first bring the source cup into a useful shared workspace, then align the rim above the target, then generate an appropriate tilt, and only then observe material transfer. The code therefore encodes the task as a stage-wise optimization problem rather than a single flat objective.

Stage A: workspace Stage B: pour-point and tilt Stage C: bead transfer Fabrics IK Warmstart reset Asymmetric actor-critic

Reward Structure and Stage A / Stage B

The local pour_v3 redesign uses an additive reward instead of a deep chain of binary gates. This is important because each term supplies gradient at the moment when that behavior should matter.

R_total = R_A + R_B + R_C + w_success R_success - w_spill C_spill R_A = R_hold + w_dist exp[-k_d max(d_cup_xy - d_sat, 0)] + w_demo exp[-e_demo] R_B = g_ready(d_cup_xy) * ( w_xy exp[-k_xy d_mouth_xy] + w_z exp[-((Delta z_mouth - z*) / sigma_z)^2] + w_rel tau + w_tilt tau_tgt ) R_C = g_ready(d_cup_xy) * ( w_near s_bead_near + w_in f_bead_in_target + w_cross Delta c_cross ) g_ready(d_cup_xy) = sigmoid((d0 - d_cup_xy) / delta)

Here, d_cup_xy is the source-cup center distance to the shared workspace target, d_mouth_xy is the source rim to target opening offset, Delta z_mouth is the rim clearance over the target mouth, tau is current tilt amount, and tau_tgt is the target-oriented tilt depth used to push the policy beyond shallow local minima.

Stage A: Available Workspace

The goal is to bring the source cup into a feasible pour-ready region while maintaining stable grasp. In the current code this is mainly driven by R_hold, transport distance shaping, and demo-arm pose shaping.

Operationally, the policy commands a 6D palm target, and Fabrics IK resolves this into arm motion. This stage mostly manifests through j1 / j2 / j3 / j4, which determine global reach, height, and gross arm posture.

Stage B: Pour-Point Tuning

Once the cup is near the target, the reward shifts toward rim alignment, vertical clearance, release-friendly tilt, and tilt depth. This stage mostly manifests through j5 / j6 / j7, which refine wrist orientation, local tilt, and the final pouring geometry.

Stage B does not stop at geometry. It stays linked to actual transfer through bead-based terms, which prevents the policy from learning a visually correct but non-flowing posture.

Why use a saturating transport term?

Once the cup has already entered the shared workspace, transport should stop dominating. The saturation avoids wasting policy capacity on over-optimizing approach after the task has moved into the pouring phase.

Why use a sigmoid ready gate?

A hard switch creates brittle optimization. A smooth gate lets the policy feel a gradual transition from transport to pouring, which is especially helpful when the rim is close but not perfectly aligned.

Why use bead terms?

Pure geometry does not guarantee flow. The bead-near, bead-in, and mouth-crossing terms bridge the gap between kinematic alignment and actual material transfer.

Presentation point: the reward is not arbitrary. Each term exists to preserve causal ordering and prevent a sparse-reward deadlock.

How simulation data reaches each network

Simulation State Joint states, cup poses, rim geometry, bead state, contact, and target-cup relation are generated in Isaac.
Actor Path The actor receives partial and noise-perturbed observations designed to stay closer to deployable sensing.
Critic Path The critic receives richer privileged state so value estimation is more stable than the actor alone would allow.
Learning Signal Rewards, terminations, and advantage estimation drive PPO updates over the rollout buffer.

Demo Data: Remote Teleoperation -> Digital Twin -> Agent-Readable Tensors

The intended dataset story is simple and strong: approximately 10 remote teleoperation demonstrations are collected, then converted into an Isaac-compatible digital twin representation so the policy can reuse that structure during RL.

teleoperation episodes -> joint trajectories + hand states + end-effector poses + timestamps -> Isaac-aligned HDF5 / digital twin representation -> pour-phase extraction -> normalized tensor bank -> reward reference / demonstration-guided shaping
1. Data Collection

During teleoperation, the system records right-arm joint positions, hand joint positions, reference hand joints, end-effector poses, target end-effector poses, and timestamps. In the code this information is expected through the HDF5 keys loaded by demo_pose_reference.py.

2. Digital Twin Alignment

The demonstrations must be expressed in Isaac-consistent coordinates, joint naming, and end-effector frames. This is what makes the data a digital twin rather than just a video or an arbitrary log file.

3. What the Agent Actually Understands

The current v3 path does not feed raw demo images into the actor. Instead, it converts demos into compact tensors and statistics: pose samples, mean / std, motion percentiles, and pour-phase references. The agent then feels the demos through pose-error-based reward shaping.

4. Why This Matters

A small demo set can constrain the early search space. The demonstrations tell the policy what a physically meaningful pre-pour arm posture looks like, while RL still decides how to refine tilt and transfer inside simulation.

Suggested explanation while presenting

  • The demo data is first converted into an Isaac-readable digital twin format.
  • The current local implementation uses that demo information as a reward-side reference, not as direct supervised actions.
  • This keeps RL flexible while still preventing completely unguided exploration in the early phase.

Actor / Critic / Observation View

For the audience, the most important message is that the actor and critic do not see the same world. This is deliberate.

Actor: 60D, partial, noisy

The actor receives arm joint position / velocity, finger grasp progress, source and target cup relations, pour-point geometry, source cup axes, recent palm action, and bead transfer summaries.

This is the deployable side of the policy. It is intentionally compressed and noise-injected.

Critic: 140D, privileged

The critic additionally receives full finger joint states, left-arm state, distal contact information, cup height change, and other internal signals that stabilize value learning.

This is not meant to be deployed directly. It is a training scaffold for better value estimation.
