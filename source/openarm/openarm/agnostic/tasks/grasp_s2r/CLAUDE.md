# grasp_s2r — 태스크 규칙

> 상위 규칙: [hdgp/CLAUDE.md](../../../../../../CLAUDE.md) (로그 먼저 · 증거 우선순위 · 분석 원칙)

## 태스크 정체성

**제자리 파지 → 리프트 → 목표 지점 이송 → 정지.** 팔은 처음부터 끝까지 정책이
Fabrics 를 통해 제어한다. 손은 관절공간 시너지(접촉 동결로 감쌈 생성).

계보:
- **제어 스택** = `agnostic/tasks/grasp_sensor` (Fabrics 팔 + 시너지 손 + 부팅 정합 게이트)
- **액션 규약·보상 8항** = `tesollo/right/grasp_v1` (grasp→lift→stabilize 98% 이력)
- **이송 2항(transfer·stay)·성공 재정의** = 이 트랙 신설

## 이 트랙을 만든 이유 (되돌리기 전에 읽을 것)

`grasp_sensor` 는 palm 액션이 **절대 매핑**(`palm = scale(a, 박스전체)`)이다. 저장소
공통 설정인 σ=1.0(`sigma_init const_initializer val:0` + `fixed_sigma: True` — 전 트랙
동일)과 곱해지면 매 스텝 목표가 작업공간 전역에서 재추첨된다. 08.27 실측: 지령 요청량이
**0.33~0.36 m/step 상시 포화**, 접근이 제자리 랜덤워크가 됐다.

⚠**정정(09.10).** 이 문단은 원래 "리미터는 속도만 자르고 방향의 무작위성은 못 막았다"
라고 적고 있었으나 **사실과 다르다 — 그때 리미터는 꺼져 있었다.** 08.27 cfg 기본값은
`palm_cmd_rate_limit_m = 0.0` · `palm_cmd_rate_limit_rot_deg = 0.0` 이고, 리미터는
전날 커밋 4694856c 가 "배선만, **기본 비활성 0.0** — corridor_test1 무영향" 으로 넣은
것이다. 0.33~0.36 m/step 은 그 커밋이 같이 넣은 **클램프 전 원지령 로깅**
(`fabric/palm_cmd_step_raw`) 값이고, 클램프는 일어나지 않았다.
즉 **08.27 구성에는 앵커·델타박스·리미터·EMA 가 하나도 없었다** — DEXTRAH 와 같은
맨 지령 파이프라인이었고, 박스는 오히려 더 작았다(0.45×0.77×0.45 = 0.156 m³ vs 1.68 m³).
제한 4종은 실패의 **원인이 아니라 그 뒤에 만든 처방**이다. 그러므로 "제한을 지웠어야
했다" 는 시간순으로 성립하지 않고, 아래 표의 판정(차이는 보상에 있다)이 그대로 남는다.
(런별 override 까지는 확인 못 했다 — 그 시기 dump 에 이 키가 하나도 없다.)

grasp_v1 규약은 `palm = 홈 + delta(a)` 라 **a=0 이 홈**이고 탐색이 유계 오프셋으로
묶인다. 같은 σ 에서 이 문제가 없다. → **팔 액션을 절대 매핑으로 되돌리지 말 것.**

### ★E1 보상 개편 (09.10) — 진행 중인 기준선 교체

D3(success 0.604) 를 E1 로 교체 시도 중이다. 계획서·reward-audit·판정 지표는
**`~/rl_ws/report/` 가 아니라** `~/rl_ws/repo/reports/grasp_s2r_보상개편_계획_0910.md` 에 있다.
⚠그 경로는 git 저장소가 아니다 — 사라지면 이 문단이 마지막 기록이다:

| | D3 | E1 |
|---|---|---|
| `lift_height_ref` / `lift_weight` | 0.06 / 30 | **0.12 / 10** |
| `transfer_weight` / `_sharpness` | 15 / 6 | **30 / 10** |
| `success_weight` / `stay_weight` | 20 / 8 | **8 / 12** |
| `approach_weight` (+`_still_floor`) | 2 (없음) | **6 (0.5)** |
| `grasp_weight` | 4 | **8** |
| `object_scale_mass` | (1,1) | **(0.5, 2.5)** |
| `wrench_force/torque_scale` | 0 / 0 | **5.0 / 0.5 (W1)** |

근거 셋: ①lift 가 6cm~목표에서 경사 0(실현 20.05/step = 총 36.6% 가 위치무관 상수)
②목표 진입이 계단(마지막 3.5cm 를 transfer 가 3.63 으로 덮는데 진입 순간 success 가 ~28)
③접근·파지가 명목 6.4% → 실현 0.18%.
**지면 위 표의 D3 열로 전부 되돌린다.** 개별 항 귀속은 불가능하다(11개 동시 변경).

### ★액션 매핑과 보상 형태는 한 묶음이다 (09.10 신설)

위 금지는 절대 매핑 자체가 나빠서가 아니다. **DEXTRAH 는 절대 매핑으로 잘 돈다** —
`compute_absolute_action(a, lo, hi)` 한 줄로 **1.68 m³** 박스 전체에 매핑하고 앵커도
변화율 제한도 EMA 도 없다. 박스는 우리가 더 **작다** — s2r 현행 프로필 박스 0.135 m³,
08.27 절대매핑 박스 0.156 m³ 로 각각 12.4배·10.8배 작다. 작은 박스는 절대 매핑에
**유리한** 쪽이므로 08.27 실패의 변명이 못 된다. 차이는 **보상**에 있다.

|  | 액션 매핑 | 보상 | 결과 |
|---|---|---|---|
| DEXTRAH | 절대(1.68 m³) | 4항 전부 `w·exp(−k·d)`, **게이트 0개** | 동작 |
| 우리 08.27 | 절대(0.156 m³, **필터 0종** — 리미터 off) | 게이트 사다리 | **랜덤워크, 실패** |
| 우리 현행 | 앵커+델타+박스클램프+리미터 | 게이트 사다리 | 동작 (success 0.740) |
| ? | 앵커+델타 | dense | **미시험** |

규칙:

> **액션 매핑이 만드는 탐색 분포와, 보상이 0 이 아닌 영역이 겹쳐야 한다.**
> - 절대 매핑은 탐색을 박스 전체로 퍼뜨린다 → 보상도 박스 전체에서 **0 이 되지 않아야**
>   한다(`exp(−k·d)` 처럼). 그래야 랜덤워크에도 경사가 남는다.
> - 보상이 좁은 게이트 뒤에 있으면 → 매핑이 탐색을 **그 게이트 근처로 모아야** 한다
>   (앵커+델타). 우리 예산의 79.8% 가 접촉 래치 하나 뒤에 있으므로 여기 해당한다.
>
> **둘 중 하나만 바꾸면 반대쪽이 무효가 된다.** 보상을 dense 로 바꾸지 않은 채 절대
> 매핑으로 돌아가면 08.27 이 재발하고, 매핑을 그대로 둔 채 게이트를 더 조이면 앵커가
> 감당하던 몫이 커진다.

⚠**형태가 이미 exp 라는 것과 그 항이 살아 있다는 것은 다르다.** 우리 `approach` 는
`2.0·exp(−(12·d_n + 8·d_l))` 로 이미 DEXTRAH 형태인데, 앞에 `pre_lift_gate`(이진,
실측 듀티 0.151)와 `palm_still = exp(−10·‖v_palm‖)` 이 곱해져 실집행이 명목의
**1.1%** 다. `palm_still` 은 구조적 긴장을 만든다 — 다가가려면 움직여야 하는데
움직이면 깎인다(0.05 m/s 에서 ×0.61, 0.15 m/s 에서 ×0.22). 그 항을 손대기 전에
`reward_cond/approach`(09.10 신설)로 **조건부 값**부터 볼 것. all-env 평균은
"항이 죽었다"와 "구간이 짧다"를 구분하지 못한다.

## 핵심 계약 (계약 테스트가 잠근다)

| 계약 | 왜 |
|---|---|
| palm = **홈 기준 델타**, 홈은 박스에 안 잘림 | 위 랜덤워크 |
| 래치는 **보상 단계 표시 전용** | grasp_v1 의 z 램프 스크립트를 걷어낸 것이 이 트랙의 목적 |
| fabric 손 상태를 **실제 자세로 동기화** | 끊으면 fabric 이 없는 자기충돌을 피하려 팔을 민다(실측 palm_err 475mm·5kN) |
| 적분은 `_step_fabric` 한 곳 | `_apply_action` 에서 돌리면 fabric 시간이 2배 |
| body **하나당** 접촉 센서 하나 | 다중 body 단일 센서는 `force_matrix_w` 무증상 0 |
| goal 은 **정착고** 기준 | 스폰 패드가 리프트 기준에 실리는 이중 패딩 사고 |
| 밀림 감쇠는 **래치 시점 스냅샷** | 실시간 변위를 쓰면 과제인 수평 이송이 처벌된다 |
| obs 에 물체 정체성 없음 | 배포 시 알 수 없는 정보 |
| 손 제어 분기는 시너지 하나 | 죽은 분기는 고칠 때 오해만 만든다 |

## 형상 의존값

**`object_grasp_z_offset = 0.03`(물체 원점↔파지 높이) 하나뿐이다.**

08.27 에 `object_grasp_radius`·`enclosure_thumb_weight` 를 제거했다. 접근 항이
컵 반경 기반 "대향 목표점"이 아니라 **손 자신의 대향 중점**(엄지 팁과 4지 팁 평균의
중점)과 컵 사이 거리(`cage_dist`)를 쓰기 때문이다. 구 수식은 대향축을 접근방향의
90° 회전으로 잡아 **좌/우 부호가 임의**였고, 그래서 엄지 목표가 실제 엄지의 반대편에
놓여 손목을 뒤집어야 도달 가능한 자세를 요구했다 — 사용자 GUI 관찰 "4지는 붙는데
엄지가 걸린다"의 원인이고, 실측으로 `grip_frac 0.20` 인데 `wrap_frac` 이 2,228 iter
내내 0.000 이었다.

## 핵심 지표 (TFEvents)

| 키 | 봐야 할 것 |
|---|---|
| `stage/{grasp,lift,transfer,stay}` | 사다리 도달률 — **단조**여야 한다 |
| `task/wrap_frac` | 감쌈 깊이(per-finger mid AND dist). 리프트 후 침식하면 `wrap_retention` 가 작동하는지 |
| `task/goal_dist` · `task/stay_run` | 이송·정지 |
| `fabric/palm_cmd_step_raw` | 클램프 **전** 요청량 — 리미터 포화율 |
| `fabric/joint_err_mean` · `palm_err_mean` | 팔 추종. 정상 0.06 rad / 0.16 m 대역 |
| `fabric/joint_err_max` | ★오픈루프 적분 격차의 **최대**. 평균은 막힘 구간을 묻는다 |
| `task/close_gate` · `task/cage_ctr_dist` | 닫기 게이트. ★중심은 palm 강체·거리는 3D — 팔이 정지한 구간에서 `syn_close` 와 상관이 붙으면 되먹임 재발이다 |
| `gate/contact_persistence` | ★`grip_frac` 과 **동행**해야 한다. 혼자 1.0 으로 가면 소수 손가락 파밍이다 |
| `gate/disp_factor` | 래치 시점 밀림 감쇠 |
| `task/abnormal_rate` · `contact/force_max` | 물리 건강 |

## 수정 규칙

1. reward/gate/weight 변경 전 **reward-audit 통과** (`~/.claude/skills/reward-audit/`).
2. obs/action 차원 변경 금지(명시 요청 없이). 변경 시 warmstart 전면 무효.
3. 한 번에 하나의 가설. 변경 후 **예상 지표 이동 방향**을 명시할 것.
4. 판정은 **학습 스모크의 건강 지표**로 한다 — zero-action probe 는 판별력이 없다
   (08.27 에 v4/v5 를 구분 못 해 오진을 유발했다).
5. 학습 스모크 게이트: `ep_len` 상승 · `abnormal ≈ 0` · `joint_err < 0.1` ·
   `palm_err < 0.20` · `force_max < 50N`.
